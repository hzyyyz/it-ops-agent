# 增量知识库更新设计

## 目标与现状

本阶段实现总计划中的「仅更新变化的 chunk」。现有 `VectorStoreService.load_document()` 用 `md5.text` 记录整文件 MD5：文件修改后会新增所有 chunk，但旧 chunk 仍留在 Chroma。现有项目没有 YAML 版本表，因此不继续依赖外部清单；Chroma 中的 ID、来源和内容是索引的实际状态。

## 方案

考虑了整文件重建、外部 YAML 清单和按 chunk 对账三种方式。整文件重建无法减少 embedding，外部清单可能与 Chroma 写入状态分叉；采用按 chunk 对账。

每个 chunk 保留来源路径、内容 MD5 和在同内容 chunk 中的出现序号。ID 根据规范化来源、PDF 页码、MD5 和序号确定，不依赖 chunk 在文档中的整体位置。每次扫描 `data/` 顶层允许的 txt/pdf 文件，先拆分，再读取 Chroma 现有的 IDs、文档和来源元数据。相同来源下 ID 和文本一致的 chunk 保留，新增或变更 chunk 写入，过期 chunk 删除；整个文件被删除时清理其旧 chunk。重复内容按出现序号区分。

首次运行会将旧版无稳定 ID 的同来源记录替换为新记录；该次迁移可能重新嵌入旧文档，之后保持增量。兼容旧版 Windows/Linux 绝对来源路径。只有成功解析和拆分的文件才会触发旧记录删除。先写入新 chunk 再删旧 chunk；部分写入失败时下次同步继续对账，并刷新同进程 BM25 缓存。同步期间持有 Chroma 目录中的跨进程锁，避免两个同步进程交错写入。返回新增、保留、删除、失败文件数量供 CLI 与日志查看。

## 范围与验证

保留当前本地命令入口，不新增匿名上传接口、用户权限或 MySQL 文档表。更新文档本身不需要调用聊天模型。使用假向量库验证首次导入、无变化重跑、局部修改、删除文件、重复 chunk、旧索引迁移及失败保护；有条件时再用本地 Chroma 验证真实持久化。
