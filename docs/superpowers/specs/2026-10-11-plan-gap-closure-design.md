# 总计划缺口收尾设计

## 范围与原则

保留现有 FastAPI、MySQL 会话、Redis 缓存、原生 Web 工作台和 Streamlit 客户端，补齐审核指出的功能缺口。旧会话和知识文件必须保留；数据库升级只做增加性变更，不重建或清空表。前端继续保持轻量，不因路线图中的 React/Vue 示例另起构建系统。

## 服务健康与接口

新增 `GET /api/health`，分别报告 API、MySQL、Redis 和知识库配置状态；模型推理与本地重排权重通过单独的就绪检查或诊断命令验证，不让普通存活探针触发昂贵模型加载。新增兼容的 `POST /api/knowledge/upload`，沿用现有文件名、10 MB 和索引同步规则，现有 `PUT /api/knowledge/{name}` 保持可用。

## 鉴权与数据边界

现有项目为本地单用户，最小可用实现是配置管理员凭据，并对聊天、会话、知识库和 Trace API 强制鉴权；健康检查和静态资源公开。Web 页面和 Streamlit 都需要提供凭据，未经授权时不可读写数据。凭据不得写入日志或仓库。多用户方案若由用户选择，则需要用户账号、会话归属、旧数据迁移和知识库权限策略，另按回答细化。

## MySQL 元数据

在已有 `sessions/messages` 之外增加 `users/documents/evaluation_results` 的明确模型与初始化。`documents` 保存文件元数据及最近索引状态，与磁盘文件和 Chroma 增量索引同步；`evaluation_results` 保存评测批次及摘要，逐题明细仍由 JSON 报告保存。初始化需可重复执行；若新增字段影响旧表，提供显式、可复查的迁移，不在 API 启动时暗改表结构。

## 效果和部署验收

基线与高级检索需要在相同数据集和相同知识库上对比，并记录 Rewrite/Reranker 是否真正启用；不能把未加载权重的融合检索写成重排结果。任务成功率区分规则代理值与人工核验。Docker Compose 使用静态配置检查以及可用时的真实容器检查；本机缺少 Docker 时如实标明不可验收项，不伪造成功结果。
